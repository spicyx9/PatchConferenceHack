# w06 : vols (Google Flights via Bright Data, fast-flights en secours)

Dossier : backend/app/providers/flights. Bloc : 07-flights.md, 13-brightdata.md.

Ordre imposé : sonde d'abord. Sans clé : structure, fast-flights local (sans proxy, résultat éventuel), fixture, tests mock.

Subagents : A sonde + Bright Data, B fast-flights + SerpApi, C aéroports, normalisation, dédup, propositions, fixture, tests.

A. `flights/probe.py` : discover_by=input_filters sur gd_mhng7wen1rw0a3gvpf pour JFK → SFO 27 au 30 octobre 2026, 1 adulte, économie, limit_per_input 10 ; sur 202 polling du snapshot ; puis collect_by_url sur 3 URLs renvoyées ; sauvegarder brut dans probes/raw/ et décrire `pricing`, `legs`, `providers` dans probes/flights.md. Règle de décision écrite dans DECISIONS.md : si legs et pricing vides, fast-flights via Bright Data devient principal.
- `flights/brightdata_provider.py` : discovery (candidats) → collect (données) → normalize. Un input par requête, requêtes en parallèle.

B. `flights/fastflights_provider.py` : installer fast-flights depuis git épinglé (`pip install git+https://github.com/AWeirdDev/flights@<commit stable, chercher le dernier tag ou le commit 7c105db cité par HaroldLeo/google-flights-mcp>`), create_query round-trip, currency USD, carry_on_bags 1, hide_separate_and_self_transfer True, integration BrightData(zone=BRIGHTDATA_UNLOCKER_ZONE) si clé sinon direct. `flights/serpapi_provider.py` : seulement `booking_options` via booking_token sur les 3 meilleures offres si SERPAPI_KEY, no_cache true.

C. `flights/airports.py` : table ville → aéroports (New York : JFK, LGA, EWR ; San Francisco : SFO, OAK, SJC ; étendre pour 20 villes US et Europe) et IATA → IANA via paquet `airportsdata`. `flights/normalize.py` : FlightOffer avec montants en chaînes, raw_text, local + UTC par segment, connection_type unknown par défaut, bagages tri-état, warnings. `flights/dedupe.py` : itinerary_id = hash des segments (carrier + numéro + départ UTC + arrivée UTC), offres multiples par itinéraire. `flights/service.py` : fan-out 9 paires, provider router (Bright Data puis fast-flights sur timeout, vide, sans prix, puis SerpApi enrichissement), cache 20 min. `flights/proposals.py` : recherche J-1 et J+1, proposition si écart > 80 $ (consommé par w11). `run(query)` avec query {origin_city, destination_city, departure_date, return_date, adults, cabin}. Makefile `probe-flights`. Fixture `fixtures/flights.json` (6 offres NYC → SF, 2 directes, 2 avec escale, 2 alternatives J-1 et J+1, prix en chaînes). Tests : normalisation, dédup, routeur, propositions.

Si BRIGHTDATA_API_KEY est absente de .env, implémente le provider avec des fixtures enregistrées et HTTP mocké, fais que les sondes terminent avec un statut explicite missing_credentials (pas une erreur), et ouvre la PR. Les sondes réelles seront relancées quand la clé arrivera.
